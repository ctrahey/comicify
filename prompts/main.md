Hi! in this directory I have started to describe a project that will be CLI tool for turning human prompts into a comic strip, with
  the express purpose of describing technical product user experience. It is motivated by https://alistapart.com/article/see-what-i-mean/
  Please look around, read that article, and iterate with me on the overall project scope and your understanding of it. You can write the tool itself in any language that makes it easy to work with the underlying intermediate representations, or rendering tools. I do fully expect that the product will use LLMs heavily - for example in clarifying the initial prompts with the author, and creating/editing the intermediate artifacts. Additionaly, it is expected that _some_ of the rendering will be done by an LLM - but if it is at all possible, please avoid this! This is a critical part of the task here: make the rendering as deterministic as possible based in the VCS-trackable intermediate representations, and lean on LLMs/GenAI for editing them. This could mean that some visual artifacts move from rendering layer concerns into intermediate-representation form. Naturally we want to strike a balance here. Lean on SVG to the extent that the visual prompts allow, and you _are_ welcome to use LLM during rendering - just bias strongly toward determinism.

  I expect that a big part of this project will be the prompts that we use internally to make sure the comic-author prompts are sufficient, to convert them to the structured intermediate forms, to generate art or proto-art, etc... These prompts should be managed cleanly in this source tree. Please do not assume any specific model provider, but you may assume standard LLM interfaces. I am not strongly opinionated on which SDKs or libraries you use, but have heard good things about Pydantic's tools for working heavily with structured representations with LLMs. So I will not be surprised if you select Python and use these libraries. 

  Please feel free to ask me clarifying questions about the project. Not that there is potential confusion because we are describing the development of a product (this Comicify CLI tool) that itself will relate to developing products (such products will flow from the minds of our users) - so we might need to be careful in our wordings.

  I have written one sample prompt, which you can use to understand how I think product developers (our users) will use the tool, and we can try this example as we go and develop others.

  I expect to see us use LLM calls with well-specified system prompts. We'll likely include a perspective there on what a good product comic is. There should be distinct system prompts for the different moments in our product UX.

  # System prompts
  During Clarification / initial ingest of the author's prompts, we will want to focus on coherence, and if we feel the prompt is sufficient to derive a clean story arc, if we can identify a sane number of characters and moments, etc. This is likely a sort of evaluation-focused first pass. Then we can move into a structured set of clarification prompts, where we get the LLM to suggest questions that will help us in the goal of capturing the required vision from the author in an interactive CLI session. The clarifications should be saved in some files we track (not necessarily edits to the author's prompt, unless we implement some sort of file-naming scheme where we leave it untouched, then create a suffix-appended variant filename and render out our "clarified" version of the prompt for downstream use.

  With the clarifications in place, we prompt the LLM for our structured intermediates. This can and probably should be many focused inference calls, and we should consider if each one needs the full context document, or if it is wiser to narrow the context down - for example, when we are prompting for a structured character profile, do we really need the narative aspects in context? likely no. We'll get stronger determinism/repeatability and likely better token efficiency by creating a prompt just for this task, implying a multi-step workflow for each structured artifact we create.

  Finally, the rendering itself might include some LLM inference, and notably we should probably "look at it and evaluate it".
